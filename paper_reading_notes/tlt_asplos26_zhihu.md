# TLT：把 reasoning RL 的长尾 rollout，变成可利用的系统机会

> 对于复杂依赖问题，通常有两种解决办法：第一种是真的把执行时间降下来，比如本文用 SD 直接缩短长尾 rollout；第二种是把资源利用里的 bubble 填上，比如本文用长尾阶段空出来的 GPU 去训练和维护 drafter。

这篇文章想解决的问题很简单：在 reasoning RL 里，`rollout` 往往是整轮训练里最慢的一段，而且会出现明显的长尾。很多短回答早就结束了，只剩少量很长的回答拖着全局进度。TLT 做的事，就是一边想办法让这些尾巴更快结束，一边把已经空出来的资源拿来干别的有价值的工作。

本文主线分三段：

1. `RL` 和 `SD` 分别在干什么。
2. `SD` 什么时候有收益，什么时候反而不值。
3. `TLT` 具体是怎么把“减关键路径”和“填 bubble”组合起来的。

## 1. RL 和 SD 是什么

### 1.1 RL 在这里是什么意思

监督学习更像“给模型标准答案”；而 RL 更像“先让模型自己做，再根据最后结果好不好来调它”。

这在推理任务里很自然，因为很多任务都有一个特点：

- 最终结果能验
- 中间过程很难逐 token 标标准答案

比如：

- 数学题可以看最终答案对不对
- 代码题可以跑测试
- 但中间那串 reasoning trace 很难逐 token 标注

所以 RL 很适合这类“最终可判、过程难监督”的问题。

### 1.2 一轮 RL step 是怎么跑的

按本文的场景，一轮 RL step 大致是：

1. 给一批 prompt。
2. `target model` 先自己生成完整 response，这一步叫 `rollout`。
3. 对 response 做 `reward` 打分。
4. 再拿一个冻结住的旧模型做参考，比较新旧分布差得远不远。
5. 根据 reward 和这个“别偏太远”的约束，更新 target。
6. 进入下一轮。

这里有两层依赖：

- `token 级自回归依赖`：一条 response 里的每个 token 都要等前缀 token。
- `step 级完整 response 屏障`：整轮 RL step 又得等这条 response 真的生成完，后面才能做打分、参考比较和更新。

这也是为什么长尾 rollout 会拖累整轮训练。

### 1.3 Reward、Reference、Update 分别是什么

**Reward**

就是对 response 打分。数学题可以看答案，代码题可以跑测试，格式错误也可能扣分。

**Reference Model**

它可以理解成一个“冻结住的旧模型”，作用像安全绳。

每次 RL 更新后，都拿当前 `target` 和这个旧模型比一下：

- 如果 target 改得不大，那没问题。
- 如果 target 在某些 token 上突然和旧模型差得特别远，就加一个 `KL` 惩罚，把它往回拽一点。

所以它的作用不是“帮你答题”，而是防止模型为了追 reward 一下子学歪。

**Update**

就是根据前面的信号更新 target：高分回答更容易被保留，低分回答的概率被压低。

## 2. SD 到底在做什么

### 2.1 它省的不是“小模型替代大模型”

很多人第一次看 `Speculative Decoding`，会误以为它是在说“小模型替代大模型”。这不准确。

它真正做的事是：

- 先让一个小一些的 `drafter` 对后续 token 做一串猜测
- 再让 `target` 一次性检查这串猜测里哪些能接受

关键收益在于：

- 普通解码是大模型一步一步往前走
- SD 是把很多次串行 decode step，压成一次更并行的验证步

所以 SD 的核心是**减少大模型串行前进的次数**。

### 2.2 “草拟多个候选 token”到底是什么意思

假设当前前缀是：

`A B C`

普通解码会这么做：

1. target 看 `A B C`，生成下一个 token。
2. 把这个新 token 接上，再生成下一个。
3. 再接上，再生成下一个。

如果想前进 4 个 token，通常就要调 4 次大模型。

而 SD 会这么做：

1. 先让 `drafter` 猜一串后续 token，比如 `d1 d2 d3 d4`。
2. 再让 `target` 来检查这串猜测里哪些位置可以接受。

所以“草拟多个候选 token”，说白了就是：

> drafter 先把它觉得后面可能会生成出来的 token 序列猜出来。

### 2.3 target 怎么“一次检查多个位置”

这是很多人第一次看 SD 最困惑的地方。

假设把下面这一整段一起喂给 target：

`A B C d1 d2 d3`

注意，这不等于“承认 d1 d2 d3 是对的”。  
它只是让 target 在同一次前向里，对不同位置分别算出“如果前缀是这里左边这些 token，那么下一个 token 应该是什么”。

于是同一次前向里，target 实际上同时得到了：

- `P(next | A B C)`，用来检查 `d1`
- `P(next | A B C d1)`，用来检查 `d2`
- `P(next | A B C d1 d2)`，用来检查 `d3`

本质上就是：

- 同一串输入进模型
- 不同位置只能看见自己左边的 token
- 所以天然对应不同前缀

这就是为什么它能“一次检查多个位置”。

### 2.4 什么叫接受，什么叫不接受

如果 target 在检查 `d1` 时认为这个位置可以接受，那就继续看 `d2`。

如果 `d1` 不能接受，那么问题在于：

- `d2` 的检查用到的前缀是 `A B C d1`
- 但现在 `d1` 已经不成立了

所以 `d2`、`d3` 后面的检查结果也都失效，要一起丢掉。

这就是为什么 SD 通常是“从前往后连续接受一段”，一旦前面断了，后面也不能直接用。

## 3. SD 什么时候赚，什么时候亏

SD 不是永远有收益。它什么时候值，取决于四件事：

- 当前 batch 大小
- response 长度
- drafter 准不准
- 现在是不是已经进入长尾后半段

### 3.1 更容易赚钱的情况

- batch 已经变小
- response 还很长
- drafter 质量还不错

这时普通 decode 很容易吃不满 GPU，而 SD 更容易一次推进多个 token。

### 3.2 更容易亏的情况

- batch 还很大
- 序列不长
- drafter 已经过时

这时 drafter 自己的额外开销可能盖过收益。

如果猜测经常被拒，target 平均每轮还是只能前进 1 个 token，那 SD 就不值。

### 3.3 为什么 reasoning RL 的后半段特别适合 SD

一轮 rollout 往往是这样的：

- 前半段：活跃请求很多
- 中段：很多短样本已经结束
- 后半段：只剩少量长尾样本

越到后面，活跃请求越少，普通 decode 越容易吃不满 GPU。  
所以 reasoning RL 的长尾后半段，反而正是 SD 比较容易赚钱的地方。

## 4. TLT 具体做了什么

理解了前面这些，再看 TLT 就清楚了：它不是简单地“把 SD 打开”，而是同时解决三个问题：

1. 长尾 rollout 很拖时间。
2. drafter 会因为 target 持续更新而变 stale。
3. 最优的 SD 配置会随着 batch 动态变化。

### 4.1 整体思路

TLT 的结构可以看成上下两层：

- 上层 `Adaptive Rollout Engine`：负责把当前长尾 rollout 跑得更快。
- 下层 `Adaptive Drafter`：负责利用空出来的资源维护 drafter，让后面的 SD 继续有效。

一句话说就是：

> 上半部分是在减当前长尾 rollout 的执行时间，下半部分是在把长尾旁边已经出现的 bubble 填满，并顺手维持 drafter 质量。

## 5. Design A：Adaptive Rollout Engine

### 5.1 Elastic enable

不是从头到尾都开 SD。

TLT 的做法是：

- 请求还很多时先不开
- 等活跃请求数降到阈值以下再开

这样可以避免在“batch 还很大、SD 还不值”的阶段反而把系统拖慢。

### 5.2 BEG-MAB：在线选 SD 配置

这个名字看起来吓人，其实做的事情很朴素。

SD 有很多可调参数，比如：

- `Draft_Depth`
- `topK`
- `Tokens_to_Verify`

不同 batch 大小时，最适合的配置不一样。  
TLT 不想每一步都做重型搜索，所以用了一个很轻量的在线选参器。

它的做法大概是：

1. 先按当前 `batch size` 落到一个桶里。
2. 只在这个桶允许的几种 SD 配置里选。
3. 维护每个候选最近一小段窗口的收益统计。
4. 大多数时候选最近中位数收益最好的。
5. 少数时候随机试一下，避免一直卡在局部最优。

这里的收益，大致可以理解成：

> 每单位时间里，实际推进了多少 accepted tokens。

所以它在线开销很轻，因为运行时做的主要是：

- 查当前 batch 落在哪个桶
- 在小候选集里查最近统计
- 做一次轻量的探索/利用选择

不是每步都去跑一遍大搜索。

### 5.3 Bucketed CUDAGraph：按区间复用执行图

这里本质上就是分桶。

朴素做法很浪费，因为 `CUDA Graph` 对形状很敏感。如果你这样搞：

- 每个精确 batch size 都录一份图
- 每种 SD 策略再录一份图
- target 和 drafter 整套一起录

图缓存会很快爆掉。

TLT 的做法更像：

1. 不给 `batch=17、18、19` 各录一份，而是让一个 batch 区间共用一组图。
2. target 图和 drafter 图拆开录，避免参数组合乘法爆炸。
3. 能共用的策略再合并。

所以它省下来的主要是：

> `CUDA Graph` 图缓存本身占的显存

不是模型参数显存，也不是 KV cache。

运行时就很轻：

- 看当前 batch 落在哪个桶里
- 选定对应策略
- 直接取对应图 replay

不是临时重新录图。

## 6. Design B：Adaptive Drafter

### 6.1 单层 drafter

TLT 没有训练一个很重的新 drafter，而是尽量把 drafter 做小，只训练很小的一层。

好处有两个：

- 更容易频繁更新
- 推理额外开销更低

### 6.2 Spot training：bubble 里训练 drafter

当 rollout 进入长尾阶段时，很多短回答先结束了，一部分 GPU worker 会先闲下来。

TLT 没让这些资源空着，而是把它们拿去做 `spot training`，也就是低优先级地训练 drafter。

关键边界要说清楚：

- 这些空出来的 GPU 不是直接去“并行帮当前长尾 token 算”
- 当前尾巴真正的直接加速，还是来自已经启用的 SD

`spot training` 更稳妥的作用是：

- 让 drafter 不要快速过时
- 让后续 RL steps 的 SD 继续有效

### 6.3 DataBuffer：复用 rollout 已经算过的中间结果

这是本文另一个很实用的点。

训练 drafter 时，一个很大的浪费是：

- rollout 时 target 已经把前缀都算过一遍了
- 如果 spot training 又拿同一批样本重新跑一遍 `target prefill`
- 就等于把最贵的部分重复算了一遍

TLT 的做法是：

1. rollout / inference 时，target 本来就会算出一串 `hidden states` 和对应 token。
2. 把这些中间结果顺手存进 `host memory` 里的 `DataBuffer`。
3. spot training 直接读取这些现成特征训练 drafter。

这样就不必为了同一批样本，重跑一遍昂贵的 target prefill。

另外，`DataBuffer` 还会跨 RL step 保留，优先补上一轮留下来的长序列。  
原因是如果只用“当前这一步先结束的样本”，那训练数据很容易偏短；而长尾样本反而少。把上一轮缓存的长序列也混进来，可以缓解这种偏置。

## 7. 最后一句话总结

TLT 真正有意思的地方，不是某一个单独 trick，而是把两种思路合在一起了：

- 一条线是 `SD`，直接缩短当前长尾 rollout 的关键路径。
- 另一条线是 `spot training + DataBuffer`，把已经出现的 bubble 利用起来，顺手维持 drafter 质量。

所以它不是单纯“让推理更快”，而是把 reasoning RL 里最烦人的长尾，变成了系统上可以利用的机会。
